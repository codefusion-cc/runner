# Map

| Path | What |
| --- | --- |
| `crates/image` (`cf-image`) | The guest image: `Manifest`, `verify` (signature, hashes, sizes, version, not older than the newest accepted), `write_release`, the embedded kernel and initramfs (`build.rs` reads `target/guest`), and `store`: installed images under `<state>/images/<version>/rootfs.img`, each verified in a folder of the Runner's own before it is used, one install at a time (a lock on the store's folder), only the files the signed list names, with the newest accepted build time in `accepted.json`. `store::is_version` says which names a version may have. Tests in `tests/verify.rs`, `tests/embedded.rs`, `tests/store.rs`. `trusted-key.txt` is the public key of the image signing key. |
| `crates/guest-proto` (`cf-guest-proto`) | What the vm-host and the guest supervisor say to each other over vsock port 6000: frames (4 bytes of length, JSON), `HostMessage`, `GuestMessage`, `Task` (probe, format the scratch disk, a job; `Job::blocked` carries the networks the Mac is in), `Secret` (prints nothing). What the guest sends is a job's to forge: the host reads it with `read_guest_message` only, which takes 64 KiB a frame (`MAX_GUEST_FRAME`) and clips every text (length, control and direction characters). Tests in `tests/protocol.rs`. |
| `crates/vmm` (`cf-vmm`) | The seam to the hypervisor: `Vmm`, `Vm` (channel, wait, stop, kill), `VmSpec`, `ExitCell` (a machine's end, said once, waited for with a limit), `Vm::resident`, what of the host's memory a machine holds, `COMMAND_LINE` and `SEND_TIMEOUT`, the same under both monitors, and `testing::FakeVmm`, a machine a test scripts (`hold` sets what its machines hold). |
| `crates/vmm-vz` (`cf-vmm-vz`) | `VzVmm`: Virtualization.framework through `objc2-virtualization`, each machine on its own queue, disks by serial, NAT, vsock (a write the guest does not read fails after 5 s), the console to a file, fixed memory with no balloon device. `Holder` (`holder.rs`) finds the framework's process that runs a machine by the machine's own files it holds open (kernel, console, writable disks) and reads its footprint less what macOS compressed, through a task name port (`Vm::resident`; `tests/holder.rs` against real processes). macOS only. |
| `crates/vmhost` (`cf-vmhost`) | One job in one machine, the body of `codefusion-runner vm`. `lib.rs` has the contract with the daemon: the `JobRequest` on standard input, `run/<job>.json` (`JobState`, read back with `JobState::read`; `out_of_memory` answers yes, no or unknown), with `resident_bytes`, what the machine holds of the host's memory, at each heartbeat, the control socket `run/<job>.sock` (`control`), the folders (`Layout`). Every file and the socket are this user's alone (`write_private`), and a folder others can write to boots nothing. `machine.rs` is the job's state machine with every wait (pure, `tests/machine.rs`): `Limits` holds them, `Limits::longest_run` and `longest_life` are the bounds no job and no stop passes, and the guest's word never picks the end by itself. `driver.rs` runs it against a `Vmm` (`tests/driver.rs`, with `FakeVmm`), `scratch.rs` keeps one formatted empty disk per image and size and clones it (clonefile on a Mac, FICLONE on Linux, else a copy of its data that keeps its holes; `tests/scratch.rs`), `task.rs` runs a small task in a machine, `host_net.rs` lists the host's networks for the guest's firewall (`host_networks`, `tests/host_net.rs`). On Linux the `Layout` also has `machines/` (each running machine's folder) and `programs/` (cloud-hypervisor, unpacked). |
| `crates/supervisor` (`cf-supervisor`) | PID 1 of the guest, a static `aarch64-unknown-linux-musl` binary. `src/lib.rs` is what it decides, tested on any host (`tests/decisions.rs`): `firewall` (the guest's rules, written with `cf-nft`; `BLOCKED` and `beside`, the networks next to the machine and those the Mac is in), `dhcp`, `oom` (the kernel's report: `read_records` takes the kernel's own lines only, never what a process wrote into the log), `outcome` (how a container ended, and never well without its launcher's report), `processes`, `environment`, `tell` (what a job's log is told). `src/linux/` is what it does: `init` (root, modules, the channel), `net`, `job` (disks, cgroup, the watch loop), `container` (namespaces, the image's user; the launcher and the first process are closed to the job's root), `hook` (the Actions runner's job hooks). CI lints `src/linux/` with clippy for the musl target, and lints and tests it on Linux. |
| `crates/nft` (`cf-nft`) | nf_tables rules without the `nft` program. `lib.rs` is the model (`Match`, `Rule` and `Rule::new`, `Chain` on a `Hook`, `Table` in a `Family`: inet, bridge, netdev) and `decide`, what a rule set does with a packet (pure). `encode.rs` turns tables into one netlink batch (`batch`, `Load::Replace` swaps the whole ruleset in one transaction) and refuses what the kernel would; `decode.rs` reads the kernel's messages back (`read`). `apply` and `list` (Linux) talk to the kernel through `cf-netlink`. `BLOCKED` is the one list of private and special ranges, used by the guest's firewall and by the host's in front of a Linux machine. Tests: `tests/nft.rs` (bytes `nft` 1.0.6 wrote, recorded in `tests/nft/`), `tests/model.rs` (a model of the kernel's expressions against `decide`, round trips), `tests/kernel.rs` (Linux: applied and listed back in a fresh user and network namespace). |
| `crates/netlink` (`cf-netlink`) | Netlink itself, for any protocol: `message`, `attribute`, `attribute_str` (a NUL-ended text), `nested`, `messages` and `attributes` to read them back, and on Linux the `Socket` that sends requests and reads every answer (`request`, `dump`), with its own `Error`. Users: `cf-nft` (nf_tables), `cf-vmm-ch` (rtnetlink). Tests in `tests/wire.rs`. |
| `crates/vmm-ch` (`cf-vmm-ch`) | `ChVmm`: machines on Linux, cloud-hypervisor under KVM, one process per machine (`machine.rs`, Linux). Each machine has a cgroup of its own under the part of the tree delegated to the Runner (`cgroup.rs`: memory at its size and `overhead`, no swap (a kernel without a swap account per cgroup only on a host that swaps to nothing), `pids.max`, the cpuset of its cores, `cgroup.kill`, `wait_empty` woken by `cgroup.events`; `memory.current` is `Vm::resident`; `own` and `enter_host` for a test suite that shares its delegated cgroup), its vCPUs on the host's fast cores that it may use (`cpus.rs` with `cf_host_linux::fast_cpus`, `--host-cpus` overrides). With a network it runs under the system's pasta (`programs::pasta`: found on `PATH`, refused when another user could change it or what it links to, tried when the first machine with a network starts; `apt install passt`, 2023-03 or newer) in a user and network namespace; the hidden `vm-sandbox` subcommand of the binary (`sandbox.rs`) makes the guest's tap, loads `firewall.rs` onto it (netdev ingress: ARP, DHCP and DNS to pasta on the gateway, IPv4 to the internet; drops `BLOCKED`, 127/8 and every network of the host, IPv6 and everything else), bridges it with pasta's device (`link.rs`, rtnetlink), and starts the monitor without capabilities and without user namespaces in a PID, cgroup, mount and empty network namespace of its own (the tap's descriptor its only way out), no file it writes growing past the largest it is shown, its root a read-only tmpfs with only what `Sandbox::for_machine` shows it (its program, the guest's files, its console and folder, `/dev/kvm`, `/dev/urandom`) and a `/proc` of its own, then reports how it ended (`ending.rs`). `command.rs` builds both command lines, `events.rs` reads `--event-monitor`, `vsock.rs` the CONNECT handshake. cloud-hypervisor is pinned in `pins.rs`, fetched into `target/vmm-programs` and embedded by `build.rs` (arm64 Linux), unpacked into `<state>/programs` and checked before each machine (`programs.rs`). Tests: unit tests of everything pure, `tests/isolation.rs` (Linux: a stand-in guest on a veth pair behind the real pasta, guard and firewall; each blocked target a test of its own), `tests/monitor_root.rs` (Linux, no harness: a stand-in monitor in the real sandbox tries the host's files, processes and mounts, and under pasta tries to send past its tap), `tests/kvm.rs` (Linux with KVM, no harness: how a real machine ends, a panic, a stop, a kill, its cgroup's OOM and a dead monitor; it skips without `/dev/kvm` and the guest, `CF_REQUIRE_KVM=1` makes that a failure). |
| `crates/runner` (`codefusion-runner`) | The binary. `commands.rs`: `version` (the package's version and the commit, which `build.rs` reads from git or `CF_COMMIT`), `image verify`, `image install`, `vm` (the vm-host, `src/vm.rs`), `boot-proof`, `vmm` (Linux: the cloud-hypervisor the build carries, which `install` and an update ask of a program), and the service's commands in `service.rs` (macOS and Linux): `daemon` (what the service manager runs; ends on SIGTERM; one per state folder, held by a lock on `<state>/runner.lock`), `enroll` (the console's one-time code on standard input, read with the terminal's echo off by `hidden.rs`, which gives the terminal back on every way out, a signal included; the token to `<state>/console-token`, 0600, never printed), `check [--github]` (what an install needs, and the memory at that moment against the budget's floor with the sizes that fit; with `--github` what GitHub shows, changing nothing there and nothing in the state folder), `install` (copies the program to `<state>/bin`, writes the service manager's entry, refuses while a machine stands), `uninstall [--leave] [--purge]` (refused while a Runner started by hand holds the state folder; a Mac without a usable token goes without telling the console). `config.rs` is the configuration file (refused when others can write it; `use` required on a Mac; on Linux `dedicated` or left out) and, on a Mac, the refusal of the cf-runners manager's own name and of external volumes; `manager.rs` is `ServiceManager`, the seam to the service manager; `launchd.rs` the agent `cc.codefusion.vm-runner` in the person's session (`plist`, `Agent`; `stop` waits past `ExitTimeOut` and decides by whether launchd still has the agent, not by what `bootout` says); `systemd.rs` (Linux) the user unit `codefusion-runner.service` (`unit`, with every path quoted for systemd or refused; `UserUnit` over an injected `systemctl --user`, the real one ended after 100 s; `stop` waits past `TimeoutStopSec` and decides by `ActiveState`); `linux.rs` the lines `check` adds on Linux (`Facts`, `lines`: KVM, lingering, delegated controllers, user namespaces, pasta, `noexec`, each with the root command that fixes it). `update.rs`: `CheckoutUpdate`, the `SelfUpdate` of a host that built the Runner, for the console's `update`: in the checkout the program was built from (`build.rs` writes it down, with `CARGO_HOME`, `RUSTUP_HOME` and `CARGO_BUILD_JOBS`), only when it is the config's `build_folder`, clean and at a commit (`own`), fetches `origin main`, refuses a main that does not contain the running commit, builds with `cargo xtask build` at low priority into `logs/update.log` and ends a build that takes longer than 45 minutes or outlasts the daemon, and keeps the program it checked as `bin/codefusion-runner.next`; `install` places that one, keeps the running program as `bin/codefusion-runner.prev` and writes `update.json` first; `guard`, run before the daemon reads its configuration, counts the new program's starts and puts the one before back after `MAX_STARTS`, and `ended_in_order` takes back the count of a start that ended as asked. `runner.entitlements` is signed into it. |
| `crates/budget` (`cf-budget`) | Admission, with no I/O: `Budget` (`observe`, `claim`, `confirm`, `assign` and `withdraw` for a job GitHub assigned without asking (`assign_in_turn` and `confirm_in_turn` with its `Turn`: `line` puts main-branch and deploy jobs first, repositories in turn, none passed over past `DEFER_LIMIT`; `set_turn` when what a waiting job stands for changed; `make_room` holds back every other size, `making-room`, and puts the size first in line), `adopt`, `usage`, `release`, `hold`, and `status`, which names every slot with how it started and every waiting job with what keeps it), the pure `admit`, `Settings` (every number, `for_host` has the defaults; `for_headless` those of a Linux host nobody sits at, which reserves what the host needs, `HEADLESS_HOST_USE`, and caps the sizes so that each machine fits with its overhead), `Size` and its labels, the `Host` trait with `HostReading`, `Battery`, what a host's page shows of its battery, and `FakeHost`, the host tests script (`read_takes` lets a read take time before and after the reading gets its time; `tests/fake_host.rs`). Tests: `admission`, `assigned`, `headless` (the rule at 4, 7.75, 8, 16 and 32 GiB and its boundaries), `levels`, `making_room`, `races`, `properties`, `turns`. |
| `crates/clock` (`cf-clock`) | `now`: the two clocks the budget counts time by, read from the host (Linux: `CLOCK_MONOTONIC` and `CLOCK_BOOTTIME`; macOS: `CLOCK_UPTIME_RAW` and `CLOCK_MONOTONIC_RAW`). Both host crates' `Host::now`. |
| `crates/host-macos` (`cf-host-macos`) | `MacHost` reads macOS behind `cf_budget::Host` (page counts, pressure, swap, idle time, thermal, power, disk); `Raw` and `reading` are the arithmetic. For the console's page: `boot_time`, `model` (chip and model, `model_name`), `battery` (what `pmset -g batt` prints, read by `battery_in`, as `cf_budget::Battery`), `host_name`, `load`, `cpu_percent`. `program_of` says which program a process runs (the daemon's `is_ours`, `Holder`). `backup`: `exclude_from_backup` marks a folder the Runner made as skipped by Time Machine (the sticky exclusion `tmutil addexclusion` sets, an extended attribute), `exclude_with` is the decision behind the `Attributes` edge; the daemon, `enroll`, `install` and `image install` mark the state folder (the daemon's `Mac::keep_state`, a failure is a logged line, never fatal), and a cache folder to come goes through the same call when it is made. `examples/host-probe.rs` prints a Mac's readings. |
| `crates/host-linux` (`cf-host-linux`) | `LinuxHost` reads Linux behind `cf_budget::Host`: MemAvailable, swap, swap-outs (`swapouts_of`: `pswpout`, but with zram in `/proc/swaps` only what is in use on swap that is not zram, since a page in zram stays in memory and PSI says when memory is short; `pswpout` again when `/proc/swaps` cannot be read), PSI (`/proc/pressure/memory`, Normal when the kernel has none), the thermal zones by their own trip points, `/sys/class/power_supply` (a host with no battery runs on the mains; a device's own battery, such as a mouse's, is left out unread), the state folder's disk by `statvfs`; idle time is none on a headless host. Every reader takes a root folder, so tests run against trees of files on any OS. `parse` reads each file, never more than `MAX_FILE_BYTES` (`counter` is one value of a `name value` file, also a cgroup's); `Raw` and `reading` are the arithmetic, with what each field means in the doc comment of `reading`. `fast_cpus` (the kind of core, by `midr_el1`, of the highest `cpu_capacity`, for `Settings::for_headless`). For the console's page: `boot_session` (`boot_id`), `boot_time`, `model` (device tree, else DMI), `battery`, `host_name`, `load`, `cpu_percent`. `process` and `program_of` say which program a process runs and when it started, read twice around the program so a number that went to another process in between names none; `started_at` moves with a step of the wall clock, `started_ticks` with `boot_session` does not. Tests: `fixtures.rs` (an RK3588 board's files, broken in every way), `parse.rs` (with properties), `real.rs` (Linux only: this machine against `free`, `df`, `getconf`). `examples/linux-probe.rs` prints a Linux host's readings and the headless budget. |
| `crates/lifecycle` (`cf-lifecycle`) | `Slot`: the state machine of one slot and its job (events in, effects out, watchdogs, `saved` and `restore` for a daemon restart; `on` answers every phase and event with no catch-all arm, keeps a word of a job in every phase, and ends a slot as `no-job` only on `Event::Unregistered`, GitHub's 204; `Asking` is the phase of a slot that asks for its registration's removal, entered at the idle limit or on `Retire`; `Slot::hear` replays GitHub's stored word on a saved slot), and `StartBreaker` (`admit` before a claim, `holds` for the budget's hold). `tests/model.rs` searches every state it can reach. |
| `crates/scaleset` (`cf-scaleset`) | The scale set protocol: `ScaleSetClient` (scale sets, sessions, one-job JIT configs, runner removal; `runner_by_name`; admin token kept until 120 s before it expires by GitHub's clock, replaced once on 401), `runner_busy`, the REST view of whether an Actions runner holds a job, `MessageSession` (long poll, ack, acquire), `listen` with the `Scaler` trait (handle, then ack; duplicates acked only; shutdown interrupts only the wait), `Backoff` and `supervise`. A token goes only to the API's origin and to hosts of `ACTIONS_HOST`: an address the service hands back that is elsewhere is refused. A registration whose answer was lost, or that names no runner, is removed again. Every status and malformed body is an `Error`. `examples/github_probe.rs` is the real check against a throwaway repository (prints no token). Tests in `tests/`, run against `cf-fake-github`; `github_rules.rs` holds the fake to what GitHub was seen to do (`docs/github-protocol.md`). |
| `crates/daemon` (`cf-daemon`) | The service. `machines.rs`: `Machines` joins the budget, the lifecycle of each slot and the vm-hosts: a job GitHub assigned is counted (`assign`), started when memory allows (a machine counts with what its vm-host read it holds of the Mac's memory, `count_held`, its job's peak only when that is not known; the log says once when it is not, or is more than the machine is counted with, `Budget::host_bytes`), registered just in time, watched every tick, and ended once with an `EndKind` (`ends.rs`); `restore` adopts what a Runner before left from the records (`records.rs`, `DiskStore`; a record stores facts, `up`, `ran_job`, `completed`, `unregistered`, and carries the `RULES` it was written under; `Record::agrees` says its facts agree, and `Record::upgrade` is the one place that reads an older Runner's record: its beliefs cleared, GitHub's stored word replayed; a current record that disagrees is an error) and the vm-hosts that still answer, in the same start of the Mac (`kern.bootsessionuuid`, not the boot time, which moves with the clock); one that is silent or wrote nothing yet is killed, and so is what has no record. A tick looks at the vm-hosts without the machines' lock, so a vm-host that hangs keeps no listener waiting. What the polls in flight may still offer GitHub is kept (`Offer`): every answer a listener got since all bells last rang, since many scale sets of one size each ask at their own moment. The last slot taken rings their bells at once, room that went or came back with the Mac's memory at a look, at most every 5 s, so no poll in flight goes on offering a slot that is gone, or none while there is one. An open Mac whose other programs leave no memory for a size it serves says so in the log and is closed for `memory` in the console's report (`Snapshot::short_of`); one that would carry the size without its own machines is full, not short. `Snapshot::rooms` is what one more machine of each size meets, for the report's `sizes` and each scale set's capacity: how many fit, the budget's word when none does, `never` for a size the settings never run, and for memory what it needs and lacks. `making.rs`: `Making`, room made for a larger size. A job that waits for the room the Mac's own machines hold, all of them smaller, while the empty Mac would run it, has every other size held back until it starts, for `MAKE_ROOM_LIMIT` (30 min) at most and then none for as long; its scale set offers a place in line while GitHub has the job back, for `TAKEN_BACK_WAIT` (2 min); an empty Mac whose other programs hold the room gives up after `NO_ROOM_WAIT`. A size whose polls found no room for `STARVED_AFTER` (10 min) is offered a place before any of its jobs is assigned; a size the empty Mac cannot run never is. `vms.rs`: `Vms`, the seam to `codefusion-runner vm`, and `VmHosts`, the real one. It writes each vm-host's process and start time to `run/<job>.pid` (0600) before it hands it the job, so the Runner that starts next can end one that hangs before its first state. A signal goes only to a child whose exit was not collected, to a process that answers on the job's socket, or to one that runs the Runner's binary, is not the Runner and started no later than the time written down for it (`is_ours`, through `Platform::process`): a number that went to a later process is sent nothing. `service.rs`: `Service` (`discover` repositories and labels, one supervised listener per scale set, `sweep` of registrations nothing stands behind, `report` to the console with the job events of the outbox and how long jobs handed here waited while nothing ran, with a WARN after `STALL_WARN_AFTER`; the sweep is the one place that removes a registration: those of slots in `Asking`, and of machines that ended while theirs stands, after `RESULT_WAIT` for one whose guest came up with no word of a job; each answer goes to `Machines::answered(runner, Answer)`: `Removed` (204) is no job, `Gone` (404) under a guest that came up is a job over, `Refused` (422) a job that runs, a job implied so is stored as inferred, `survey` for `check`, `retire` for `uninstall`, `run`). What the Runner believes about each machine and its job, which evidence moves it and what is written before what is done, is `docs/job-state.md`. `scaler.rs`: `Scaler` (reserve before acquire, release for jobs taken elsewhere, converge on assigned jobs, each place in line with the turn of the assigned job it stands for (`Slots::set_turn`), offers taken overdue first, then main and deploy jobs, retire surplus after `IDLE_GRACE` (`Hosts::retire`: idle machines ask for their registration's removal, which the sweep does); before a session opens, `reconcile` asks GitHub's REST view of each Actions runner it believes waits, since messages go with a closed session, and a busy one took a job (`Answer::Busy`); a session opens only at start, after GitHub forgot one, after a listener failed, or after a restart), `Roster` (an Actions runner belongs to a repository's scale set: GitHub numbers scale sets within a repository, so the number alone names none), `turns.rs`: `turn_of`, whether a job is the main branch's or a deploy, from its workflow's ref, name and event. `names` (runner and scale set names, `ServePolicy`; a scale set's name ends in a hash of its repository and labels, so two repositories that ask for the same labels each get their own). `update.rs`: `SelfUpdate`, `Pending` in `update.json`, `at_start` (`Trying`, `GoBack` after `MAX_STARTS` starts that did not stay up for `STAYS_UP`, `Failed`, also when a program before could not be put back: `Pending::failed`); the service builds while jobs run, then holds new jobs until no machine stands and no slot promised to GitHub is left (`Machines::coming`), installs and ends (`update`, `restart`; one at a time, the result said once by the Runner that starts next). `platform/`: `host_service`, the service on a real host, which the binary and `cargo xtask it` both build, over a `Platform` (`This` is this build's): what differs between systems and nothing else: the host's reader and the budget's settings (`Settings::for_host`; on Linux `for_headless` with the fast cores), the boot session, host name, model and what the console's page shows (`extras`), `keep_state` (Time Machine; nothing on Linux), `fit` (the virtualization entitlement; on Linux `codefusion-runner vmm` says the build carries cloud-hypervisor), `process` (program and start, for `is_ours`; on Linux `cf_host_linux::process`), `program` (the program alone, for a kill's wait), `vm_hosts` and `SERVICE_LOG`. `mac.rs` is macOS, `linux.rs` Linux, where each vm-host starts in a systemd scope of its own (`VmHosts::in_scopes`, `systemd-run --user --scope -p Delegate=yes`, `codefusion-runner-<job>.scope`), whose delegated cgroup it claims for its machines, and `user_bus_env` finds the user's systemd under `sudo -iu`, and not another user's that `su` left in the environment (`this_user` names the user from the user database). `tests/scopes.rs` (Linux, no harness) starts a stand-in vm-host so and checks it claims the scope's cgroup. `log.rs`: `Lines`, the log file that is rolled over. `testing` has the fakes, and `CrashingStore`, records at which a test makes the daemon die between any two writes. Tests: `machines.rs` (every end kind, a crash at every step), `records.rs` (every record main and earlier builds could have written, read by `Record::upgrade`), `interleavings.rs` (the property test), `schedules.rs` (the property test of the job facts against a GitHub that keeps the truth: crashes at any write, every answer to a removal, lost and late messages, records left in older formats; with pinned schedules), `offers.rs` (the property test of what several listeners of one size offer), `making_room.rs` (the mini's cf-6g job against the cf-2g ones that keep coming), `calm.rs` (the calm minute against time that passes within a look, and against everything that is really wrong), `service.rs` (GitHub's and the console's failures; the property test that no job gets two machines, a session opens only for a cause, a job that waits while a machine fits moves at GitHub's next look, and every job that ran is heard, start and end once each, however many messages went with a session, with a stale or failing REST view, a crash between any two writes, five minutes that take an assignment back, removals that fail until GitHub recovers, and an uninstall in the middle; machines that boot slowly, so a start or an end comes before the Runner saw one up; no VM whose job runs is stopped, and every single write's facts agree (`CrashingStore::disagreements`); a second property aims the same checks at surplus removals), `scaler.rs`, `listening.rs`. |
| `crates/ghapp` (`cf-ghapp`) | The GitHub App client: `AppCredentials::load` (`app.json` + `app.pem`, which must be 0600), the App JWT (iat now-60 s, exp now+9 min, clock skew learned from the `Date` header), installation tokens (cached, one request at a time), repositories, workflow files (the caller names the largest file to read), repository variables, registration tokens; `Http::new(timeout, retry)` with retries (429 and 5xx with jitter, `Retry-After`), HTTPS only (or this machine itself), redirects only to the same origin, at most `MAX_BODY_BYTES` of an answer and 100 pages of a listing. ## Run

- Build and boot proof: `cargo xtask build && target/release/codefusion-runner boot-proof`. The binary needs
  the virtualization entitlement (the build adds it, ad hoc) and an Apple silicon Mac.
- The guest supervisor builds with `rust-lld` (see `.cargo/config.toml`), so no cross toolchain is needed.
- What the budget sees on a Mac: `cargo run -p cf-host-macos --example host-probe`. It only reads and prints; compare
  with `vm_stat` and `sysctl kern.memorystatus_vm_pressure_level vm.swapusage`.
- On Linux, `cargo test -p cf-nft --test kernel` applies rules in a user and network namespace of its own; with
  `CF_REQUIRE_NAMESPACES=1` a host that does not allow that fails instead of skipping. Ubuntu 24.04 allows it only
  with `kernel.apparmor_restrict_unprivileged_userns=0`.
- What the budget sees on Linux: `cargo run -p cf-host-linux --example linux-probe [state folder]`; compare with
  `free -b`, `/proc/vmstat` and `/proc/pressure/memory`.
- GitHub's hosted Macs cannot boot VMs (no nested virtualization), so CI never runs `boot-proof`; it runs on a Mac.
- On Linux (arm64, KVM): `apt install passt`, `cargo xtask build` (it fetches the pinned cloud-hypervisor into
  `target/vmm-programs/` first; `cargo xtask cloud-hypervisor` alone does only that), and run `boot-proof` or `vm` in
  a cgroup delegated to the user, for example `systemd-run --user --scope -p Delegate=yes`, with `/dev/kvm` open to
  the user. Machines need user namespaces, as above for Ubuntu. `cargo test -p cf-vmm-ch --test isolation`
  and `--test monitor_root` need pasta and user namespaces, not KVM; `--test kvm` needs KVM, `cargo xtask guest` and the
  delegated cgroup. `cargo xtask it` runs on such a host too, its Mac-only scenarios left out.
- Real machines: `gh release download <image tag> -R codefusion-cc/runner -D target/it/release`, then
  `cargo xtask build && cargo xtask it` (`--only oom,firewall` for some). It installs the release through the store,
  which verifies it, and needs a network for the firewall and GitHub checks.
- Under launchd the state folder and the binary are on the Mac's own disk: an agent that touches another volume
  waits for the owner's consent in the middle of a system call, for good, and hears no SIGTERM there. `it`'s
  `launchd` scenario keeps all it touches in the temporary folder for that reason.
- The service by hand, without launchd: `codefusion-runner daemon --config <file>` until Ctrl-C. `check --config
  <file> --github` first says what is missing and which repositories and labels GitHub shows.
- The vm-host is counted as its machine's size and `Settings::VM_HOST_OVERHEAD` (192 MiB). `cargo xtask it --only
  full-memory` measures it again: a 4 GB machine whose job holds all it gets, and a 1 GB one. `boot-proof` prints what
  its machine held of the Mac's memory, which says the vm-host finds the framework's process on this macOS.
- A job with a deadline of `d` seconds is over `d` + 30 s after its machine was ready at the latest
  (`Limits::longest_run`: 20 s to end by itself, 10 s for the guest to say so), and its vm-host is gone 130 s
  after that at the latest (`Limits::longest_life`). A stop from the daemon or a signal brings the end sooner, never
  later.
- The service on Linux: a unit of the user's systemd (`install`), each vm-host in a scope of its own. Not one cgroup
  delegated to the service: systemd 252 starts a unit's main process in the unit's own cgroup, which the kernel refuses
  (`EBUSY`, the unit fails with `219/CGROUP` at every restart) once controllers are enabled there for machines, and
  only systemd 254's `DelegateSubgroup=` would avoid that.

### Windows later

The seams a Windows host would fill, with nothing above them reshaped: a `cf_budget::Host` from
`GlobalMemoryStatusEx` and the performance counters, and a `Platform` whose `process` reads process creation times;
a `cf_vmm::Vmm` on Hyper-V or the Windows Hypervisor Platform; a `ServiceManager` on the Service Control Manager with
recovery set to restart on every exit, the vm-hosts started to break away from the service's job object; Job Objects
and WFP in place of cgroups, namespaces and nftables; the console-mode API in place of termios for `hidden.rs`.

## Image signing

Ed25519 over `SHA256SUMS` as unpadded base64url in `SHA256SUMS.sig` (Magnetar's scheme). The list names `image.json`
and every file `image.json` names, and nothing else. `image.json` carries the version, each file's size and hash, the
hash of the whole root filesystem and when the release was built, so all of that is signed with it.

`verify` checks the signature first (strictly: no weak key, no altered signature), then that the list and the manifest
agree, then every byte. It answers for the moment it read the files: use them from a folder only the Runner can write
to. `verify` also takes the build time of the newest image the machine has accepted and refuses an older one, so an
old release offered again under its old name does not come back. `image verify` passes 0 and only reads; `image install` copies the release into the store, verifies the copy
against the time the store keeps and moves that time forward.

The key signs image lists only. Anything else that gets signed later, such as the Runner's own updates, gets a key of
its own, so a list signed for one purpose never passes for another.

`xtask guest` signs the embedded bundle with a key made for that build, written to `target/guest/bundle-key.txt`; the
embedded self-check catches a damaged binary only. The trusted key never signs a bundle, which has no root filesystem
and no build time; `xtask release` signs nothing without a root filesystem. Downloaded images are checked against
`trusted-key.txt`.

### Where the key is, and a new one

The secret half is the secret `IMAGE_SIGNING_KEY` of the repository's `image` environment, which only `main` may
deploy to. `image.yml`'s `publish` job is the only one that names that environment. It checks out and compiles
nothing: it runs the signer and the verifier that the `build` job of the same run made on main, with the key on
standard input. Pull requests run the `build` job, which has no secret.

To replace the key (it leaked, or its holder changes):

1. `cargo xtask keygen <file>` writes the new secret half to `<file>` and prints the public half.
2. `gh secret set IMAGE_SIGNING_KEY --env image < <file>`, then delete `<file>`.
3. Put the public half into `crates/image/trusted-key.txt` and merge. The next image is signed with the new key.

A Runner built before step 3 refuses images signed with the new key and keeps the image it has until it is updated;
one built after it refuses every image signed with the old key. There is one trusted key at a time on purpose.

### The kernel

`xtask/src/kernel.rs` pins Alpine's `linux-virt` package by SHA-256; a build fetches it over HTTPS and refuses any
other bytes. The file says how the pin was checked against Alpine's own signature and how to move it.
