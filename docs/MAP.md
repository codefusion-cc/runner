What the guest sends is a job's to forge: the host reads it with `read_guest_message` only, which takes 64 KiB a frame (`MAX_GUEST_FRAME`) and clips every text (length, control and direction characters). Tests in `tests/protocol.rs`. |

| `crates/vmhost` (`cf-vmhost`) | One job in one machine, the body of `codefusion-runner vm`. `lib.rs` has the contract with the daemon: the `JobRequest` on standard input, `run/<job>.json` (`JobState`, read back with `JobState::read`; `out_of_memory` answers yes, no or unknown), the control socket `run/<job>.sock` (`control`), the folders (`Layout`). Every file and the socket are this user's alone (`write_private`), and a folder others can write to boots nothing. `machine.rs` is the job's state machine with every wait (pure, `tests/machine.rs`): `Limits` holds them, `Limits::longest_run` and `longest_life` are the bounds no job and no stop passes, and the guest's word never picks the end by itself. `driver.rs` runs it against a `Vmm` (`tests/driver.rs`, with `FakeVmm`), `scratch.rs` keeps one formatted empty disk per image and size and clones it, `task.rs` runs a small task in a machine, `host_net.rs` lists the Mac's networks for the guest's firewall (`host_networks`, `tests/host_net.rs`). |
| `crates/supervisor` (`cf-supervisor`) | PID 1 of the guest, a static `aarch64-unknown-linux-musl` binary. `src/lib.rs` is what it decides, tested on any host (`tests/decisions.rs`): `firewall` (the rules and their nf_tables netlink form; `BLOCKED` and `beside`, the networks next to the machine and those the Mac is in), `dhcp`, `oom` (the kernel's report: `read_records` takes the kernel's own lines only, never what a process wrote into the log), `outcome` (how a container ended, and never well without its launcher's report), `processes`, `environment`, `tell` (what a job's log is told). `src/linux/` is what it does: `init` (root, modules, the channel), `net`, `job` (disks, cgroup, the watch loop), `container` (namespaces, the image's user; the launcher and the first process are closed to the job's root), `hook` (the Actions runner's job hooks). CI lints `src/linux/` with clippy for the musl target. |
| `crates/runner` (`codefusion-runner`) | The binary. `commands.rs`: `version` (the package's version and the commit, which `build.rs` reads from git or `CF_COMMIT`), `image verify`, `image install`, `vm` (the vm-host, `src/vm.rs`), `boot-proof`, and the service's commands in `service.rs` (macOS): `daemon` (what launchd runs; ends on SIGTERM; one per state folder, held by a lock on `<state>/runner.lock`), `enroll` (the console's one-time code on standard input, read with the terminal's echo off by `hidden.rs`, which gives the terminal back on every way out, a signal included; the token to `<state>/console-token`, 0600, never printed), `check [--github]` (what an install needs, and the memory at that moment against the budget's floor with the sizes that fit; with `--github` what GitHub shows, changing nothing there and nothing in the state folder), `install` (copies the program to `<state>/bin`, writes the agent, refuses while a machine stands), `uninstall [--leave] [--purge]` (refused while a Runner started by hand holds the state folder; a Mac without a usable token goes without telling the console). `config.rs` is the configuration file (refused when others can write it) and the refusal of the cf-runners manager's own name; `launchd.rs` the agent `cc.codefusion.vm-runner` in the person's session (`plist`, `Agent`; `stop` waits past `ExitTimeOut` and decides by whether launchd still has the agent, not by what `bootout` says). `runner.entitlements` is signed into it. |
| `crates/budget` (`cf-budget`) | Admission, with no I/O: `Budget` (`observe`, `claim`, `confirm`, `assign` and `withdraw` for a job GitHub assigned without asking, `adopt`, `usage`, `release`, `hold`, and `status`, which names every slot with how it started and every waiting job with what keeps it), the pure `admit`, `Settings` (every number, `for_host` has the defaults), `Size` and its labels, and the `Host` trait with `HostReading`. Tests: `admission`, `assigned`, `levels`, `races`, `properties`. |
| `crates/host-macos` (`cf-host-macos`) | `MacHost` reads macOS behind `cf_budget::Host` (page counts, pressure, swap, idle time, thermal, power, disk); `Raw` and `reading` are the arithmetic; `FakeHost` is the host tests script. For the console's page: `boot_time`, `model` (chip and model, `model_name`), `battery` (what `pmset -g batt` prints, read by `battery_in`), `host_name`, `load`, `cpu_percent`. `FakeHost::read_takes` lets a read take time before and after the reading gets its time. `backup`: `exclude_from_backup` marks a folder the Runner made as skipped by Time Machine (the sticky exclusion `tmutil addexclusion` sets, an extended attribute), `exclude_with` is the decision behind the `Attributes` edge; the daemon, `enroll`, `install` and `image install` mark the state folder (`keep_out_of_backups` in `service.rs`, a failure is a logged line, never fatal), and a cache folder to come goes through the same call when it is made. `examples/host-probe.rs` prints a Mac's readings. |

| `crates/scaleset` (`cf-scaleset`) | The scale set protocol: `ScaleSetClient` (scale sets, sessions, one-job JIT configs, runner removal; `runner_by_name`; admin token kept until 120 s before it expires by GitHub's clock, replaced once on 401), `MessageSession` (long poll, ack, acquire), `listen` with the `Scaler` trait (handle, then ack; duplicates acked only; shutdown interrupts only the wait), `Backoff` and `supervise`. | `crates/daemon` (`cf-daemon`) | The service. `machines.rs`: `Machines` joins the budget, the lifecycle of each slot and the vm-hosts: a job GitHub assigned is counted (`assign`), started when memory allows, registered just in time, watched every tick, and ended once with an `EndKind` (`ends.rs`); `restore` adopts what a Runner before left from the records (`records.rs`, `DiskStore`) and the vm-hosts that still answer, in the same start of the Mac (`kern.bootsessionuuid`, not the boot time, which moves with the clock); one that is silent or wrote nothing yet is killed, and so is what has no record. A tick looks at the vm-hosts without the machines' lock, so a vm-host that hangs keeps no listener waiting. Room a poll in flight may still offer GitHub and that is gone (the last slot taken, memory the Mac's other programs took, `Offer`) rings the listeners' bell, from a look at most every 5 s; an open Mac with no memory for a size it serves says so in the log and is closed for `memory` in the console's report (`short_of`). `vms.rs`: `Vms`, the seam to `codefusion-runner vm`, and `VmHosts`, the real one. A signal goes only to a child whose exit was not collected, to a process that answers on the job's socket, or to one that runs the Runner's binary, is not the Runner and started no later than the time written down for it (`is_ours`): a number that went to a later process is sent nothing. `service.rs`: `Service` (`discover` repositories and labels, one supervised listener per scale set, `sweep` of registrations nothing stands behind, `report` to the console with the job events of the outbox, `survey` for `check`, `retire` for `uninstall`, `run`). `scaler.rs`: `Scaler` (reserve before acquire, release for jobs taken elsewhere, converge on assigned jobs, retire surplus after `IDLE_GRACE`), `Roster` (an Actions runner belongs to a repository's scale set: GitHub numbers scale sets within a repository, so the number alone names none), `names` (runner and scale set names, `ServePolicy`; a scale set's name ends in a hash of its repository and labels, so two repositories that ask for the same labels each get their own). `mac.rs`: `mac_service`, the service on a real Mac, which the binary and `cargo xtask it` both build. `log.rs`: `Lines`, the log file that is rolled over. `testing` has the fakes. ## Run

- Build and boot proof: `cargo xtask build && target/release/codefusion-runner boot-proof`. The binary needs
  the virtualization entitlement (the build adds it, ad hoc) and an Apple silicon Mac.
- The guest supervisor builds with `rust-lld` (see `.cargo/config.toml`), so no cross toolchain is needed.
- What the budget sees on a Mac: `cargo run -p cf-host-macos --example host-probe`. It only reads and prints; compare
  with `vm_stat` and `sysctl kern.memorystatus_vm_pressure_level vm.swapusage`.
- GitHub's hosted Macs cannot boot VMs (no nested virtualization), so CI never runs `boot-proof`; it runs on a Mac.
- Real machines: `gh release download <image tag> -R codefusion-cc/runner -D target/it/release`, then
  `cargo xtask build && cargo xtask it` (`--only oom,firewall` for some). It installs the release through the store,
  which verifies it, and needs a network for the firewall and GitHub checks.
- Under launchd the state folder and the binary are on the Mac's own disk: an agent that touches another volume
  waits for the owner's consent in the middle of a system call, for good, and hears no SIGTERM there. `it`'s
  `launchd` scenario keeps all it touches in the temporary folder for that reason.
- The service by hand, without launchd: `codefusion-runner daemon --config <file>` until Ctrl-C. `check --config
  <file> --github` first says what is missing and which repositories and labels GitHub shows.
- The vm-host is counted as its machine's size and `Settings::VM_HOST_OVERHEAD` (192 MiB). `cargo xtask it --only
  full-memory` measures it again: a 4 GB machine whose job holds all it gets, and a 1 GB one.
- A job with a deadline of `d` seconds is over `d` + 30 s after its machine was ready at the latest
  (`Limits::longest_run`: 20 s to end by itself, 10 s for the guest to say so), and its vm-host is gone 130 s
  after that at the latest (`Limits::longest_life`). A stop from the daemon or a signal brings the end sooner, never
  later.

## Image signing

Ed25519 over `SHA256SUMS` as unpadded base64url in `SHA256SUMS.sig` (Magnetar's scheme). The list names `image.json`
and every file `image.json` names, and nothing else. `image.json` carries the version, each file's size and hash, the
hash of the whole root filesystem and when the release was built, so all of that is signed with it.

`verify` checks the signature first (strictly: no weak key, no altered signature), then that the list and the manifest
agree, then every byte. It answers for the moment it read the files: use them from a folder only the Runner can write
to. `verify` also takes the build time of the newest image the machine has accepted and refuses an older one, so an
old release offered again under its old name does not come back. `image verify` passes 0 and only reads; `image install` copies the release into the store, verifies the copy
against the time the store keeps and moves that time forward.

The key signs image lists only. Anything else that gets signed later, such as the Runner's own updates, gets a key of
its own, so a list signed for one purpose never passes for another.

`xtask guest` signs the embedded bundle with a key made for that build, written to `target/guest/bundle-key.txt`; the
embedded self-check catches a damaged binary only. The trusted key never signs a bundle, which has no root filesystem
and no build time; `xtask release` signs nothing without a root filesystem. Downloaded images are checked against
`trusted-key.txt`.

### Where the key is, and a new one

The secret half is the secret `IMAGE_SIGNING_KEY` of the repository's `image` environment, which only `main` may
deploy to. `image.yml`'s `publish` job is the only one that names that environment. It checks out and compiles
nothing: it runs the signer and the verifier that the `build` job of the same run made on main, with the key on
standard input. Pull requests run the `build` job, which has no secret.

To replace the key (it leaked, or its holder changes):

1. `cargo xtask keygen <file>` writes the new secret half to `<file>` and prints the public half.
2. `gh secret set IMAGE_SIGNING_KEY --env image < <file>`, then delete `<file>`.
3. Put the public half into `crates/image/trusted-key.txt` and merge. The next image is signed with the new key.

A Runner built before step 3 refuses images signed with the new key and keeps the image it has until it is updated;
one built after it refuses every image signed with the old key. There is one trusted key at a time on purpose.

### The kernel

`xtask/src/kernel.rs` pins Alpine's `linux-virt` package by SHA-256; a build fetches it over HTTPS and refuses any
other bytes. The file says how the pin was checked against Alpine's own signature and how to move it.
